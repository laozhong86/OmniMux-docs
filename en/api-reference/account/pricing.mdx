- Public catalog API. No authentication is required.
- Every live model row carries a `contract` object with the model-level capability envelope and, since Contract v2, an executable operation list.

## Identity

| Field | Value |
| --- | --- |
| Series | Account |
| Capability | Public pricing |

## Endpoint

| Method | Path |
| --- | --- |
| `GET` | `/api/pricing` |

Base URL: `https://omnimux.ai`

## Response

### 200

`data` is an array of models. Each row includes `model_name`, `quota_type`, `model_ratio`, `model_price`, `enable_groups`, `default_group`, `group_order`, and `contract`.

The API sorts model rows by update time, creation time, and metadata ID, in descending order for each field. When all three values tie, it sorts by `model_name` in ascending lexicographic order.

The top-level `pricing_version` identifies the pricing display contract; the current value is `"model-group-display-v1"`.

| Display field | Meaning |
| --- | --- |
| `enable_groups` | Enabled groups for the model, sorted by group name in ascending lexicographic order. |
| `default_group` | Server-selected default group for this model. When non-empty, it is guaranteed to belong to both the model's `enable_groups` and the caller's `usable_group`. If an administrator-configured default group is unavailable to the caller, this is the empty string `""`. Without explicit configuration, selection falls back in order to the caller's group, `"default"`, then the first available group in `group_order`. |
| `group_order` | Model-level group display order. Each group in `enable_groups` appears exactly once. The API returns the configured order when it is valid. When that order is missing or invalid, it follows the ascending group-name order in `enable_groups`. `auto_groups` lists automatic routing candidates. |

The optional top-level `defaults` map recommends a model per operation (`chat`, `vision_chat`, `text_to_image`, `text_to_video`, `text_to_music`, `speech_to_text`). Every value references a model present in the same response with non-empty `enable_groups`; absent recommendations are omitted.

The `contract` object is descriptive only. It never participates in billing, quota or settlement.

| Contract field | Meaning |
| --- | --- |
| `schemaVersion` | Contract shape. `"2.0"` means `operations` is an object array. |
| `contractVersion` | Per-model content hash. Use it to cache one model without re-reading the whole payload. |
| `operations[]` | Executable operations. Each has `id`, `executable`, `inputs[]`, `parameters[]`, and `output.type`. |
| `operations[].modeKind` | Optional localization key for video modes. `image_reference` identifies Muse image references, and `multimodal_reference` identifies Seedance multimodal references. Use the operation's `id` in the request. |
| `operation_ids[]` | The same operation ids as a string array, for v1-compatible clients. |
| `unknowns[]` | Field paths whose value the governance spec did not establish. Missing fields are not defaults. |
| `reference_images` / `reference_videos` / `reference_audios` | Declared reference-media limits and accepted formats. |
| `reasoning_efforts` | Optional map from reasoning level to the upstream wire value for text models. |
| `default_reasoning_effort` | Optional default level; when present it is one of the `reasoning_efforts` keys. |

An operation input carries `slot`, `type`, `role`, `firstItemRole`, `required`, `min`, `max`, `allowedMimes`, `maxSizeMb` and duration bounds when declared. A parameter carries `name`, `type`, `enum`, `minimum`, `maximum`, `step`, `default`, `fixed`, and `limitSource`.

`executable: false` means the operation is documented by the vendor but this gateway does not execute it; clients must not submit it.

## Video group capabilities

`GET /api/pricing` model rows and `GET /api/model_contract/:model` responses may include `effective_video` beside `contract` for video models with `contract.gateway_protocol: "video_generations"` or registered verified group rules. It is the account-scoped view of the groups the caller can select: `groups` maps each group to an array of complete operation variants, and `version` changes when that view's capability content changes. A model without a video capability view omits `effective_video`; legacy callers continue to use the model-level `contract` and the existing invocation path.

| Field or state | Meaning |
| --- | --- |
| `effective_video.version` | Content version of the current account's group view. The model-level contract version remains `contract.contractVersion`. |
| `effective_video.groups` | Maps each account-selectable group to complete operation variants. Groups outside the caller's `usable_group` are not included. |
| `effective_video` omitted | No account-scoped group view is published; use the model-level `contract` and the existing call path. |
| Empty `groups` object or empty group array | An empty object means this account has zero publishable groups. An empty array means the selected group has zero verified variants; do not fall back to another group. |

A variant contains `id`, optional `gateway_protocol`, `modeKind`, `inputs`, `parameters`, and `output`. The same operation `id` can appear in multiple variants with different media limits or parameter constraints. Match the whole request against one variant, including slot counts and required parameters; `required: true` means the caller must send the value explicitly. For ordered image references, `firstItemRole: "first_frame"` marks the first reference image as the starting frame. A verified profile may narrow `modeKind` and the accepted media roles relative to the model-level contract.

### Protocol inheritance

Read the selected variant's `gateway_protocol` first; when absent, inherit the model-level `contract.gateway_protocol`. When all groups use the same protocol as `contract.gateway_protocol`, variants omit this field. Mixed-protocol models (or variants whose protocol differs from the model default) publish `gateway_protocol` on each variant, and the selected group's variant protocol is authoritative.

| Protocol | Create | Query |
| --- | --- | --- |
| `openai_video` | `POST /v1/videos` | `GET /v1/videos/{task_id}` |
| `video_generations` | `POST /v1/video/generations` | `GET /v1/video/generations/{task_id}` |

For a model whose default protocol is `openai_video`, selecting a native `video_generations` variant uses `POST /v1/video/generations` with `X-OmniMux-Video-Protocol: video_generations`; query that task with `GET /v1/video/generations/{task_id}`. The `openai_video` default remains `POST /v1/videos` and `GET /v1/videos/{task_id}`. Native requests without the header keep the existing model default decoding behavior for legacy clients.

### Selection and retries

The catalog shows the groups available to the account at read time. Select a group explicitly with a `model@group` model value; that group constrains the submission and every retry, and the request must match one complete variant in `effective_video.groups[group]`. An accepted task is queried by its original task record and protocol, even if catalog or group rules change later. `400 video_capability_mismatch` means no available verified candidate accepts the combination; `503` means no verified candidate is currently available.

For Seedance 2.5 requests with a source or reference video, supply `operation` as `video_edit`, `video_extend`, or `video_multi_ref`; the gateway derives the upstream task type. The corresponding `omni_reference_task_type` value `edit`, `extend`, or `reference` also works. Requests with `draft: true` or a nonempty `draft_task_id` return HTTP `400`.

## Related endpoint

`GET /api/model_contract/:model` returns `data.contract` and `data.version`, the version of the whole static contract document. For video models with a video capability view, `data.effective_video` uses the same structure and account scope as the pricing row. A model without a governance spec returns `404`.
