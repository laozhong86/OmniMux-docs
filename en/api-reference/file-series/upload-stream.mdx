> - Upload local files or raw binary data via `multipart/form-data`
> - MP4/MOV video: up to **200 MiB (209,715,200 bytes)**; other files: **100 MiB (104,857,600 bytes)**
> - Files automatically expire and are purged after **72 hours**
> - Limit of **2,000** active files per user; returns 429 when quota is exhausted
> - Auth: `Authorization: Bearer sk-...`

## Browser direct upload

<Note>
Browser direct uploads are live as of October 12, 2026. The multipart endpoint remains available.
</Note>

Use the existing `POST /api/v1/files/upload/presign` and `POST /api/v1/files/upload/confirm` endpoints (also available under `/v1/files/upload/*`), not the publishing media-presign endpoint. Ticket and confirmation calls use the existing file-upload authentication. Both accept JSON: presign requires non-empty string `file_name` and `mime_type`, a positive integer `file_size`, and optional string `upload_path`; confirm requires string `file_id` and the same integer `file_size`. The standard response uses `success` (boolean), `code` (integer), `msg` (string), and `data` on success. Ticket data contains `file_id`, `upload_url`, `upload_method`, `upload_headers` (a string-to-string map), `resource_url`, `download_url`, and `expires_at`.

Upload tickets default to **15 minutes** and cannot exceed **1 hour**. Ticket `data.expires_at` is the upload deadline, not the confirmed file's retention deadline.

1. Request a ticket with `file_name`, `mime_type`, positive `file_size` in bytes, and optional `upload_path`. The ceiling is **200 MiB (209,715,200 bytes)** for MP4/MOV video and **100 MiB (104,857,600 bytes)** for other files; a website flow may impose a lower limit. For ordinary uploads, a video MIME type or `.mp4`/`.mov` filename selects the video reading budget, but files larger than 100 MiB must also pass actual MP4/MOV container checks. Renaming a non-video file does not raise its valid limit. The reference-video browser-check purpose below has a separate policy. Base64 uploads retain the 100 MiB decoded-file limit.
2. PUT the original browser `File` as the request body to `data.upload_url`, using `data.upload_method` and every returned `data.upload_headers` value unchanged. These are the required signed headers, including `If-None-Match: *`, which prevents replay from overwriting an existing object. Do not wrap the file in `FormData`, use the site's authenticated client, or add an OmniMux Bearer header. Set `credentials: "omit"`.
3. After PUT succeeds, confirm with `file_id` and the same `file_size`. Use the confirmed URL and retention in the existing upload library only after confirmation succeeds. A ticket's `resource_url` is not proof of a confirmed file.

Fall back to multipart **only** if the ticket endpoint returns the documented **501** unsupported-storage response. Authentication, quota, network, PUT, and confirmation failures must not silently relay or retry the file; preserve the service's safe `msg`.

Confirmation checks object existence, positive size, and stored `Content-Type` metadata through R2 **HEAD**, without reading the complete object body. Actual size must equal the original ticket declaration, even if confirmation supplies a different size; type metadata must equal the ticket's normalized MIME type. Confirmation atomically activates only an owned, pending, unexpired record. Repeated or conflicting confirmation cannot replace an active object. For ordinary video uploads above 100 MiB, confirmation also reads the object to verify the complete stored size and an MP4/MOV container; a temporary read failure can be retried. This container check does **not** establish codec or decodability. These metadata checks do **not** validate the actual media format, duration, or safety. Separate reference-media preparation still applies to ordinary uploads; the reference-video purpose below uses browser checks instead.

## Reference-video browser checks

The reference-video browser-check purpose is available as of October 18, 2026. The influencer page reads and checks the original file in the browser before requesting an upload. Failed checks or unsupported source-following duration/framing produce the existing top-of-page message and prevent adding or uploading that file. The browser retains the complete metadata and submits it again for generation; duration and framing follow the reference rather than manual controls.

Presign accepts the following additional JSON fields. Multipart fallback accepts the same fields as form values; `video_metadata` must be a **JSON-encoded string** in multipart, rather than another file part.

| Field | Type in presign JSON | Required | Description |
| --- | --- | --- | --- |
| `purpose` | string | No | Use exactly `influencer_reference_video` only after the full local reference-video checks pass. Omit for ordinary uploads. |
| `video_metadata` | object | With this purpose | The raw browser-read fields below, without a `raw`, `version`, or `browserMetadata` wrapper. Missing or out-of-range declarations are rejected. These are client declarations, not server-verified media facts. |

| `video_metadata` field | Type | Description |
| --- | --- | --- |
| `duration` | number | Actual container duration in seconds; retain the measured fractional value. |
| `video_duration` | number | Actual video-track duration in seconds; retain the measured fractional value. |
| `width` | integer | Actual display width in pixels, including rotation. |
| `height` | integer | Actual display height in pixels, including rotation. |
| `frame_rate` | number | Measured video frames per second. |
| `video_codec` | string | `h264` or `hevc`. |
| `audio_codec` | string | Empty for no audio; otherwise `aac`, `mp3`, or `pcm` / `pcm_*` for MOV only. |
| `container` | string | Actual container: `mp4` or `mov`. |
| `size_bytes` | integer | Actual positive file size in bytes; must match the upload's declared size. |

The current browser-check upload purpose also requires the following declared specifications. Passing the general video-input bounds alone does not establish that the current generation service can follow the source.

| Declared specification | Current requirement |
| --- | --- |
| Container and video-track duration | Both are from 4 through 30 seconds. Let `s = round(duration)`; `s` is 4–30 and both measured durations must be within `1 / frame_rate + 0.001` seconds of that same `s`. Retain the raw values; the page displays the actual whole-second generation duration. A value such as 7.2 seconds is rejected rather than silently shortened. |
| Width and height | Each is 300–6000 pixels. |
| Total pixels | `width × height` is 407696–8295044. |
| Input width-to-height ratio | 0.4–2.5, plus the stricter source-following framing rule below. |
| Frame rate | 24–60 frames per second. |
| Source-following framing | This purpose is checked against the current 480p framing set: `16:9`, `9:16`, or `3:4`. For `n:d`, whole-pixel rounding is accepted only when `abs(width × d - height × n) ≤ (n + d) / 2`. The page additionally checks the selected output resolution; 720p currently supports only `16:9` and `9:16`. A valid reference such as `1:1` is rejected for this purpose because the current service cannot preserve its framing. |

Supply all fields with finite numeric values. The declared MIME must match `container`: `video/mp4` for MP4; `video/quicktime` or `video/x-quicktime` for MOV. In presign, `file_size` must equal `video_metadata.size_bytes`; in multipart, the file part's size and Content-Type must match those declarations. The **200 MiB (209,715,200-byte)** hard ceiling still applies. The service checks declaration bounds and consistency but does not read the file to establish media facts for this purpose.

The server binds this policy to the upload record when presign succeeds; it retains the reserved `influencer-reference/browser-upload` path and ignores a caller-supplied custom folder for this purpose. Confirmation cannot change an ordinary ticket to this purpose. Direct-upload confirmation keeps ownership, pending-state, expiry, R2 HEAD existence, exact size, and matching Content-Type checks, including for files over 100 MiB. It does **not** download the object to inspect its container, codec, duration, resolution, or decodability. Multipart still transfers the bytes through the server, but skips media-content inspection for this purpose. This policy does not label metadata as server-verified and does not change ordinary uploads or public generation API behavior.

<RequestExample>
```javascript Browser PUT
// ticket is data from a successful presign response; file is the original File.
const uploaded = await fetch(ticket.upload_url, {
  method: ticket.upload_method,
  headers: ticket.upload_headers,
  body: file,
  credentials: "omit",
});
if (!uploaded.ok) throw new Error("Direct upload failed");
// Call the authenticated confirm endpoint only after this succeeds.
```
</RequestExample>

## Form Fields (multipart/form-data)

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `file` | binary | Yes | File binary data stream |
| `upload_path` | string | No | Custom folder path (supports camelCase `uploadPath`) |
| `file_name` | string | No | Custom file name (supports camelCase `fileName`) |
| `purpose` | string | No | Use `influencer_reference_video`; see the browser-check section above. |
| `video_metadata` | JSON string | With this purpose | The complete raw metadata object encoded as a string. |
