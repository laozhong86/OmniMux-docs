- 账户管理用户 API（CLI / 无头环境登录）
- **申请码与轮询换 token 无需鉴权**；浏览器侧批准/拒绝需已登录用户会话
- 换取的 `access_token` 用于后续 `https://omnimux.ai` 用户接口，不用于收费模型生成请求

<Warning>
  下述限定权限设备凭据行为为第 3 批发布草稿，尚非部署公告。
</Warning>

## 身份

| 字段 | 值 |
| --- | --- |
| 系列 | 账户管理 |
| 能力 | 设备码登录 |

## 接口

| 步骤 | 方法 | 路径 | 鉴权 |
| --- | --- | --- | --- |
| 1. 申请设备码 | `POST` | `/api/user/device/code` | 无 |
| 2. 用户浏览器确认 | 打开 `verification_uri` | 控制台 / CLI 登录页 | 浏览器会话 |
| 3. 轮询换 token | `POST` | `/api/user/device/token` | 无 |
| 4. 批准 / 拒绝（可选，已登录会话） | `POST` | `/api/user/device/approve` · `/api/user/device/deny` | 用户会话 |

Base URL：`https://omnimux.ai`

## 鉴权说明

| 步骤 | 要求 |
| --- | --- |
| `device/code` · `device/token` | **不需要** `Authorization` / `New-Api-User` |
| `device/approve` · `device/deny` | 已登录浏览器会话；请求体含 `user_code`。批准还须在 `X-Security-Proof` 传入准确设备的验证证明；拒绝不需要证明 |
| 换得凭据之后 | 允许访问的用户接口：`Authorization: Bearer <access_token>`；`New-Api-User` 可为兼容保留，但不参与鉴权 |

网关 AI / 社交数据仍使用 `https://api.omnimux.ai` 的 `sk-` 令牌，与设备码 access token **不是同一套凭证**。见 [连接与使用](/zh/faqs/connection-usage)。

## 限定权限设备批准——发布草稿

浏览器须核对**准确设备码**，并完成 `cli.device.approve` 专用安全验证。它与手动创建凭据不是同一个操作。验证内容绑定 `device_flow_id`、规范化的 `user_code`、授权 `scopes` 和凭据的绝对到期时间 `expires_at`。原样使用服务端返回的信息，不在客户端重算期限或扩大权限。换设备、账户、会话、权限或到期时间的证明不能批准本次请求。批准和拒绝都仅限浏览器会话，个人凭据不能批准其他设备。

新设备凭据在**设备登录流程创建起 30 天**到期。即使管理员登录，也只授予个人业务权限：查询本人资料；管理和读取完整网关密钥；社媒发布；托管频道；灵感查询与分享；文件上传。准确权限为 `api_key:read`、`api_key:reveal`、`api_key:write`、`files:read`、`files:write`、`hosted:read`、`hosted:write`、`inspiration:read`、`inspiration:write`、`profile:read`、`social:read`、`social:write`。**不**授予 `usage:read`、`influencer:read`、管理员、系统、钱包写入、资料修改、账户安全修改或试用区生成权限。通俗说明见[权限指南](/zh/faqs/security)。已有资源归属、角色和计费检查仍有效。

新设备登录成功时只替换该用户的**设备凭据槽**，并清除旧单凭据，保留独立手动创建的个人凭据。设备槽被替换后，原设备凭据失效，使用它的其他设备须重新登录。过期或撤销后也须重新执行设备码登录，不会无声签发永久凭据。

原 CLI 响应字段 `access_token`、`user_id`、`username`、`token_type` 保持不变，原客户端可保存新的 `nap_` 字符串，无须因返回格式升级客户端；这不代表所有外部客户端的业务流程都已实测。明文只签发一次，之后无法从列表再次取回。仍持有旧单凭据的客户端须在统一过渡截止前重新登录。

## 请求体 / 参数

### `POST /api/user/device/code`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `client_name` | string | 否 | 客户端标识（如 `my-cli`）；不带 `user_code` 时申请新设备流程 |
| `user_code` | string | 否 | 候选版本：查询已有待批准流程的公开验证信息；不创建新流程，也不返回设备保密码 |

### `POST /api/user/device/token`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `device_code` | string | 是 | 步骤 1 返回的 `device_code` |
| `grant_type` | string | 否 | 若传则须为 `urn:ietf:params:oauth:grant-type:device_code` |

轮询间隔遵循响应中的 `interval`（默认约 5 秒）；过频会返回 `slow_down`。

## 响应

### 步骤 1 · 200（申请码）

| 字段 | 说明 |
| --- | --- |
| `data.device_code` | 设备侧保密码（用于轮询） |
| `data.user_code` | 用户在浏览器输入的短码 |
| `data.verification_uri` | 确认页 URL |
| `data.verification_uri_complete` | 预填 `user_code` 的完整 URL |
| `data.expires_in` | 有效期（秒，默认 900） |
| `data.interval` | 建议轮询间隔（秒） |
| `data.verification_scope` | 候选版本：`cli.device.approve` |
| `data.verification_context` | 候选版本：准确设备流程 ID、规范化用户码、授权权限和凭据绝对到期时间；原样传给安全验证 |

### 步骤 3 · 成功（已批准）

| 字段 | 说明 |
| --- | --- |
| `data.access_token` | `nap_` 开头的限定权限个人访问凭据；私密保存本次返回的明文 |
| `data.token_type` | `Bearer` |
| `data.user_id` | 已登录用户 ID；原客户端可保留，不用它作为鉴权依据 |
| `data.username` | 用户名 |

### 步骤 3 · 进行中 / 错误（HTTP 多为 200 + `success: false`）

| `code` | 含义 |
| --- | --- |
| `authorization_pending` | 用户尚未批准 |
| `slow_down` | 轮询过快 |
| `access_denied` | 用户拒绝 |
| `expired_token` / `invalid_grant` | 过期或无效 |

更多错误语义见 [连接与使用](/zh/faqs/connection-usage)。
